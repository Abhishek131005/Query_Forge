## 0. Project context and baseline

### 0.1 Purpose

QueryForge AI is a local Text-to-SQL application that converts natural-language questions into SQLite `SELECT` queries using TinyLlama 1.1B with a LoRA adapter, lets users upload CSV datasets, execute read-only SQL, explore results, and compare base versus fine-tuned models.

### 0.2 Existing layout (inspect and confirm)

```text
Query_Forge/
├── backend/
│   ├── __init__.py
│   ├── main.py                 # FastAPI /generate-sql, /health
│   ├── model_service.py        # TinyLlama, PEFT LoRA, base adapter toggle
│   └── requirements.txt
├── frontend/
│   ├── app.py                  # Streamlit: 4 pages
│   ├── database.py             # session-specific SQLite + CSV imports
│   ├── sql_executor.py         # SQLGlot validation, read-only SQLite execution
│   ├── requirements.txt
│   ├── README.md
│   └── .local_data/            # local generated databases, do not commit
├── models/
│   └── tinyllama-sql-lora-adapter/
│       ├── adapter_config.json
│       ├── adapter_model.safetensors
│       ├── tokenizer.json
│       ├── tokenizer_config.json
│       └── chat_template.jinja
└── .gitignore
```

### 0.3 Verified baseline from inspected source

- `backend/main.py`: `POST /generate-sql` takes `question`, `schema`, `model` (`base`/`finetuned`) and currently returns SQL, model, status.
- `backend/model_service.py`: loads the LoRA model, uses a lock, temporarily disables adapters for base inference, extracts a `SELECT`, and **rewrites intent** via `_repair_common_intent`.
- `frontend/app.py`: generates SQL via API or deterministic demo, **rewrites SQL again** using `normalize_common_query`, and currently has a combined **Generate and run query** action; it stores results/history in Streamlit session state.
- `frontend/database.py`: CSV import (10 MB, 100k rows, 100 columns), SQLite file keyed by Streamlit session state, table/schema exploration, delete.
- `frontend/sql_executor.py`: SQLGlot SQLite parser, single `SELECT` root, read-only SQLite URI, SQLite authorizer, five-second progress timeout, 500-row output cap.
- `frontend/requirements.txt` includes `sqlglot>=26,<29`.

**Known limitations to address:** postprocessing contaminates evaluation, generation triggers execution, old results can remain visible, schema widget can be stale, backend lacks inference timing/token counts, simplistic regex table rewriting fails on joins/multiple tables, no measured evaluation dashboard, limited automated tests.

### 0.4 Non-negotiable rules

1. **Do not mutate the GitHub repository automatically.** All changes must be proposed and applied locally by the developer.
2. Keep the app usable on **Windows PowerShell**, with a Python virtual environment, CPU-only PyTorch support, and optional CUDA.
3. Keep existing Streamlit pages: **AI SQL Studio**, **Database Explorer**, **Model Comparison**, **Model Intelligence**. Extend rather than discard them.
4. Never display made-up training curves, accuracy, speedups, or model comparisons. Show `Not measured` until measured.
5. Evaluation must compare the **same prompt, schema, generation settings, database snapshot, and question set** for base and fine-tuned models.
6. SQL generated by a model is **untrusted**. No arbitrary SQL execution, no writes, no unsafe SQLite extensions. Keep strict read-only execution and resource limits.
7. Do not silently correct raw model output for benchmark scoring. A separately labeled postprocessed track is optional.
8. No production claims about security, accuracy, or scalability without tests.
9. Avoid introducing cloud services, paid APIs, authentication providers, or heavy new dependencies without developer approval.
10. Keep UI styling consistent with the current dark QueryForge theme.

**Goal:** Stable, auditable Text-to-SQL flow that preserves raw predictions and prepares the application for honest evaluation.

### M3.5-01 — Split generation and execution [P0]

**File:** `frontend/app.py`

- [ ] Rename the combined `Generate and run query` button to **Generate SQL**.
- [ ] Remove `execute = run or manual_execute`; clicking Generate must **not** execute SQL.
- [ ] Keep a separate **Execute SQL** button, disabled for empty SQL.
- [ ] Generate into a session-state-backed SQL editor; allow edits before execution.
- [ ] Ensure session-state widget values are set **before** widget instantiation on the same rerun.
- [ ] On generation failure, show an error, clear stale editor SQL and results, and do not run the previous query.
- [ ] On execution failure, show an error, clear stale results, and record a failed history event.

**Acceptance:** Generate → inspect/edit → execute is a two-step workflow; generation alone never touches the query executor.

### M3.5-02 — Fix result and editor state lifecycle [P0]

**File:** `frontend/app.py`

- [ ] Use distinct session-state keys for `question`, `schema`, `sql_editor`, `query_result`, `execution_time`, `result_truncated`, `history`.
- [ ] Clear previous results when a new SQL query is generated, SQL execution fails, a table is imported/deleted, or active database changes.
- [ ] Detect **manual edits** to SQL: results from the previously executed SQL must not be presented as results of the edited SQL. Track `executed_sql` and compare with current editor content, or invalidate on edit via a callback.
- [ ] Show an explicit message when results correspond to an earlier SQL version.
- [ ] Do not erase history on ordinary Streamlit reruns; cap in-memory history (e.g., 100 entries) to prevent unbounded growth.
- [ ] Avoid double history entries with ambiguous meaning: distinguish `generated`, `executed`, `failed` events and include timestamps.

### M3.5-03 — Preserve model output; eliminate silent rewriting [P0]

**Files:** `backend/model_service.py`, `frontend/app.py`

- [ ] Stop calling `_repair_common_intent()` for normal generation.
- [ ] Stop calling `normalize_common_query()` in connected mode; remove regex table substitution and question-to-SQL rewriting.
- [ ] Keep demo-mode hardcoded SQL explicitly labeled **Demo**, and prevent it from being mistaken for a model prediction. Demo SQL is valid only for the demo schema; for imported CSV tables require a real backend or a manually entered query.

- [ ] Expose **raw_output** and **extracted_sql** (or `sql`) as separate values; do not overwrite the raw field.

- [ ] If SQL extraction is needed for the UI, make it deterministic and label it as extraction rather than generation; score raw and extracted forms separately if relevant.

**Recommended API semantics:** `raw_output` is the exact decoded completion; `sql` is a best-effort extracted SQL statement for display/execution. `postprocessed` is `false` by default. Keep backwards compatibility with the `sql` field.

**Acceptance:** A base or LoRA mistake remains visible as a mistake; multi-table joins are not silently rewritten.

## 2. Milestone 4 — Real evaluation and Model Intelligence

**Goal:** Reproducible, honest base-vs-LoRA evaluation with actual SQL validity, execution success, answer correctness, and latency metrics.

### 2.1 Evaluation design principles

- **Primary metric:** execution accuracy, where the model's query result matches a reference query's result on the same SQLite fixture.
- **Secondary metrics:** SQL parse validity, read-only safety acceptance, execution success, average/median/p95 inference latency, token count, error taxonomy, and optional exact-string match.
- **Do not equate execution success with correctness.** `SELECT * FROM employees` may run but not answer the question.
- **Do not equate SQL string match with semantic correctness.** Different valid SQL can yield the same answer.
- **Use identical conditions** for both models: benchmark, schema, prompt, generation config, device, database, and execution limits.
- **Do not tune prompts or postprocessing separately per model** during a reported comparison.
- **Prevent benchmark leakage:** don't include benchmark questions as few-shot examples; avoid claiming unseen generalization without a genuinely held-out test set.
- **Avoid training/evaluation overlap:** record dataset provenance and compare benchmark questions against known training samples when possible. If training records aren't available, label contamination risk explicitly.
- **Do not treat sample metrics as actual results.** Only render numbers from stored run records.

### M4-01 — Define evaluation benchmark and dataset [P0]

**Proposed files:** `evaluation/benchmark.json`, `evaluation/fixtures/employees.csv` or `evaluation/fixtures/benchmark.sqlite3`, `evaluation/README.md`.

- [ ] Build an initial benchmark of **30–50 questions**, then expand if time allows.
- [ ] Include easy/medium/hard questions: projections, filters, comparisons, `AND`/`OR`, `LIKE`, `IN`, `BETWEEN`, `ORDER BY`, `LIMIT`, `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `GROUP BY`, `HAVING`, distinct, dates, joins, and subqueries.
- [ ] Include at least **two related tables** and multiple join questions; avoid a benchmark entirely centered on `employees`.
- [ ] Store an unambiguous `id`, `question`, `schema_id`, `reference_sql`, `difficulty`, `tags`, and `order_sensitive` for each question.
- [ ] Include dataset/fixture version, provenance, and benchmark version.
- [ ] Ensure every reference SQL is safe, executes, and has an expected result on the fixture.
- [ ] Avoid trivial empty-answer cases dominating the benchmark; include data that differentiates plausible wrong queries.
- [ ] Mark cases with ties or nondeterministic order; define tie-handling and order-sensitive comparison rules.
- [ ] Separate **development questions** (prompt iteration) from **held-out evaluation questions** (final reported metrics).
- [ ] Never modify the held-out set after seeing model failures without recording a new benchmark version.

**Suggested benchmark record:**

```json
{
  "id": "emp_014",
  "question": "Which department has the highest average salary?",
  "schema_id": "employees_v1",
  "reference_sql": "SELECT department, AVG(salary) AS average_salary FROM employees GROUP BY department ORDER BY average_salary DESC LIMIT 1;",
  "difficulty": "medium",
  "tags": ["aggregation", "group_by", "sorting", "limit"],
  "order_sensitive": true
}
```

**Acceptance:** All reference queries pass the same read-only executor and return deterministic, reviewed expected results.

### M4-02 — Implement evaluation engine [P0]

**Proposed files:** `backend/evaluation.py` or `evaluation/runner.py`, `evaluation/metrics.py`, `evaluation/result_compare.py`.

- [ ] Load benchmark records with schema validation (Pydantic/dataclass).
- [ ] Validate benchmark fixture and reference SQL before running models.
- [ ] For each question, generate with **base** and **finetuned** using the same prompt and generation settings.
- [ ] Capture raw output, extracted SQL, inference time, generated tokens, errors, and device.
- [ ] Validate SQL syntax and safety with the same SQLGlot/SQLite policy used by the app.
- [ ] Execute generated and reference queries against **the same read-only fixture**, never against arbitrary user data by default.
- [ ] Capture query runtime, row count, truncation, execution errors, and comparison result.
- [ ] **Do not score truncated outputs as correct**; use evaluation-specific row limits and mark inconclusive cases explicitly.
- [ ] Implement normalized result comparison: normalize column order only if projection order is not required; preserve row order for `ORDER BY`/`LIMIT` or explicitly order-sensitive cases; otherwise compare row multisets (including duplicates).
- [ ] Normalize SQLite numeric representation carefully (e.g., `1` vs `1.0` where semantically equivalent); compare floats with documented tolerance; treat `NULL`, text, dates, and booleans consistently.
- [ ] Avoid accepting wrong column selections simply because values happen to coincide. Compare expected column count and, where required, names/semantics.
- [ ] Distinguish `correct`, `incorrect`, `invalid_sql`, `unsafe_sql`, `execution_error`, `timeout`, `model_error`, `inconclusive`.
- [ ] Handle empty results without automatically awarding correctness for two empty outputs; include fixture data and extra test cases where possible.
- [ ] Support a `--limit` smoke test, full benchmark, and optionally repeated runs for timing stability.
- [ ] Use a **sequential** inference loop initially to avoid memory pressure and cross-model GPU contention; ensure model lock behavior is correct.
- [ ] Make benchmark execution cancellable where feasible and save partial results without mislabeling them as complete.

**Acceptance:** Evaluation runner produces a reproducible per-question record for both models, with explicit failure reasons and no silent SQL repair.

### M4-03 — Define metrics and denominators [P0]

**Proposed file:** `evaluation/metrics.py`.

- [ ] **Parse validity rate** = syntactically parseable generated SQL / all benchmark questions.
- [ ] **Safety acceptance rate** = read-only validated SQL / all benchmark questions.
- [ ] **Execution success rate** = successfully executed model queries / all benchmark questions.
- [ ] **Execution accuracy** = result-equivalent model queries / all benchmark questions. Failures count as not correct; inconclusive cases are separately disclosed.
- [ ] **Exact SQL match** (optional, not primary) = canonicalized SQL string matches / all benchmark questions; document that semantic equivalents may differ.
- [ ] **Mean/median/p95 inference latency** computed only from actual completed generations, with sample count and CPU/GPU context.
- [ ] **Mean generated tokens** and optional tokens/second (only when time is measured consistently).
- [ ] **Per-difficulty accuracy** and **per-tag accuracy** with denominator and sample size.
- [ ] **Paired outcomes**: both correct, only base correct, only LoRA correct, neither correct.
- [ ] Optional **bootstrap confidence intervals** on paired question outcomes if sample size warrants; otherwise disclose small sample uncertainty.
- [ ] Never divide by zero; display `N/A` and the denominator when no samples exist.

**Acceptance:** Unit tests verify formulas using known toy records; all dashboard metrics match exported run data.

## 7. Decisions to make before implementation

1. **Evaluation storage:** local JSON/CSV first (recommended) or SQLite results database.
2. **Evaluation runner:** CLI first (recommended) or backend asynchronous job API.
3. **Benchmark:** synthetic, hand-reviewed SQLite fixture (recommended for reproducibility) plus optional external benchmark later.
4. **SQL output policy:** raw decoded output + extracted SQL, with no repairs (recommended).
5. **Deployment:** local single-user demo for now (recommended); public deployment requires separate hardening.
6. **Dependencies:** keep minimal; add `pytest` and optional `ruff`, avoid large framework changes.
